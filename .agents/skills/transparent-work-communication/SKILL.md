# Transparent Work Communication Skill (คู่มือการสื่อสารและรายงานความคืบหน้าแบบโปร่งใส)

ทุกครั้งที่เริ่มทำงาน ไม่ว่าจะเป็นการแก้ไขบั๊ก, การเพิ่มฟีเจอร์, หรือการตรวจสอบระบบ **ต้องอ่านและปฏิบัติตามข้อกำหนดในเอกสารนี้ทุกครั้งโดยไม่มีข้อยกเว้น**

---

## 🎯 กฎหลัก 5 ข้อที่ต้องสื่อสารและรายงานให้ผู้ใช้ทราบเสมอ

ในการตอบกลับหรือก่อนลงมือแก้ไขงานทุกขั้นตอน ต้องสื่อสารให้ผู้ใช้เข้าใจสถานะอย่างชัดเจน ครอบคลุม 5 มิติหลัก ดังนี้:

### 1. กำลังจะทำอะไร (What are you about to do?)
- บอกจุดประสงค์และเป้าหมายของขั้นตอนที่กำลังจะทำอย่างชัดเจน
- ระบุไฟล์หรือจุดที่กำลังจะเข้าไปตรวจสอบ/แก้ไข
- *ตัวอย่าง*: "ตอนนี้ผมกำลังจะเข้าไปตรวจสอบไฟล์ `AdminReorderModal.tsx` ในส่วนของการเรียกใช้ React Hooks..."

### 2. เจออะไร (What did you find / observe?)
- รายงานข้อเท็จจริงหรือผลลัพธ์ที่ตรวจพบจากโค้ด, Terminal, Network หรือ Console log
- อ้างอิงชื่อฟังก์ชัน, บรรทัดที่เกี่ยวข้อง หรือข้อความ Error ที่เกิดขึ้นจริง
- *ตัวอย่าง*: "จากการตรวจสอบหน้า Console ในภาพที่แนบมา พบข้อความ `Minified React error #310` ซึ่งบ่งชี้ว่า..."

### 3. สาเหตุตรงนี้เกิดจากอะไร (What is the root cause?)
- อธิบายที่มาที่ไปของปัญหาในเชิงเทคนิคอย่างเข้าใจง่าย
- ชี้ให้เห็นว่าทำไมระบบถึงแสดงพฤติกรรมหรือข้อผิดพลาดแบบนั้นออกมา
- *ตัวอย่าง*: "สาเหตุเกิดจากการมีคำสั่ง `if (!isOpen) return null` อยู่คั่นกลางก่อนถึง `useEffect` ทำให้..."

### 4. จะแก้ไขยังไง (How will it be fixed?)
- บอกแผนงานและแนวทางที่ใช้แก้ปัญหาอย่างเป็นรูปธรรม
- อธิบายขั้นตอนที่กำลังจะทำเพื่อแก้จุดผิดพลาดนั้นให้หายขาด
- *ตัวอย่าง*: "แนวทางแก้ไขคือ จะย้ายคำสั่ง Early Return ลงไปอยู่ด้านล่างสุดหลังจากที่ Hooks ทุกตัวประกาศเสร็จสิ้น..."

### 5. ติดตรงไหนบ้าง (What blockers or issues were encountered?)
- หากพบปัญหาหน้างาน, Build Error, คำสั่ง Terminal มีปัญหา หรือระบบรอนาน ต้องแจ้งให้ผู้ใช้ทราบทันทีตามความจริง
- ไม่นิ่งเงียบ หรือปล่อยให้ผู้ใช้รอโดยไม่ทราบว่าระบบกำลังติดปัญหาอะไรอยู่
- *ตัวอย่าง*: "ระหว่างรัน Build พบว่ามีฟังก์ชันชื่อซ้ำกัน 2 จุด ทำให้คอมไพล์ไม่ผ่าน กำลังเข้าไปเคลียร์จุดที่ซ้ำออกครับ..."
